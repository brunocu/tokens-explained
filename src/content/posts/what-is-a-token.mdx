## How does a computer store text?

A _character_ is a single letter, digit, space or punctuation mark. A computer does not store characters as shapes. It stores each one as a number, using a table that says which number belongs to which character. Such a table is called a character encoding.

Most English letters take up one byte, many other characters take several. A byte can be set in <Fact of="byteValues" /> different ways, which gives the values 0 to <Fact of="lastByteValue" />. The difference comes from history.

The first widely used table was ASCII, published in the United States in 1963 <Cite n={1} />. It had room for 128 characters, which was enough for English letters, digits and punctuation, plus a few control codes such as the one that ends a line <Cite n={1} />. Every ASCII character fit in a single byte, with room to spare.

Computers soon used that spare room for more characters, such as accented letters. But every country and every company filled it differently, so the same value could mean different letters on different machines, and text arrived garbled. Languages such as Japanese and Chinese, with thousands of characters, needed several bytes for each one and ended up with tables of their own, which did not agree with each other either <Cite n={2} />.

In 1987, engineers at Apple and Xerox began the Unicode project, which aimed to give every character in every language its own number <Cite n={3} />. Unicode decides the number, and UTF-8 decides how to store that number as bytes. UTF-8 was devised in 1992 by Ken Thompson <Cite n={4} />. It keeps the ASCII values exactly as they were and uses between one and four bytes for every other character <Cite n={4} />. Today, 99.1% of the websites whose encoding is known use it <Cite n={5} />.

For example, in ASCII and UTF-8 alike, the letter _t_ has the value <Fact of="byteOfT" />, and a space is <Fact of="byteOfSpace" />.

Here is the opening sentence of *Anna Karenina*, by Leo Tolstoy (translation by Constance Garnett)<Cite n={6} />.

> Happy families are all alike; every unhappy family is unhappy in its own way.

To the computer, the sentence is a row of byte values, each between 0 and <Fact of="lastByteValue" />. The space has a value too, because a space is a character like any other.

## What is a language model, and why numbers?

Natural language processing, or NLP, is the field of computer science whose goal is to get computers to perform useful tasks involving human language. A language model is a computational system that can predict the next word from previous words <Cite n={7} />. A language model is the kind of AI program behind chat assistants.

Inside, a language model is built from arithmetic. It multiplies and adds numbers, and letters cannot be added up, so text has to become numbers before the model can use it.

The number a model receives for a piece of text is a label, not an amount. The letter _t_ having a bigger value than the letter _a_ does not make it more important. The value only says which character it is.

## Why not feed in raw bytes?

The simplest choice is to give the model the bytes themselves. The model then needs only <Fact of="byteValues" /> different labels, one for each possible byte, and every text in every language can be written this way.

The problem is length. Take the sentence "the cat sat on the mat and the cat sat on the hat". It has <Fact of="wordCount" /> words but <Fact of="startPieces" /> bytes. A model that reads raw bytes has to work through sequences that are longer than the same text cut into words, which costs more computation <Cite n={8} />.

A better deal lies between single bytes and whole words. Imagine you keep a list of pieces of text: some are single bytes, others are longer pieces that turn up often. This list is called a vocabulary, and each piece in it is called a **token**. A token is a small piece of text that a language model reads and writes. It can be a whole word, part of a word, a single character, a space plus a word, a piece of punctuation, etc.

A program called a tokenizer cuts text into tokens from the vocabulary and turns them into numbers, called ids. It can also turn the ids back into text.

## Tokens are not words

Tokens are not the same thing as words. The same sentence can contain more tokens than words.

Many everyday words are a single token, while rare words are split into several. A space can be part of a token.

## How the numbers are assigned

Each token has an id, and the model works with those ids, not with the letters. The id is simply the token's label.

The vocabulary is a numbered list, and the id of a token is its position in the list. Counting starts at 0, so a vocabulary of V entries uses the ids 0 to V - 1. In the demo below, the vocabulary starts as the <Fact of="byteValues" /> single byte values, with the ids 0 to <Fact of="lastByteValue" />, and every new token is added at the end of the list with the next id.

Similarly to character encodings, these ids are only labels in a list. A bigger number does not mean a rarer or more important word, and a different tokenizer would give the same token a different id.

## Why not just split on spaces, or on meaning?

The obvious way to make tokens is to cut at spaces, so that every word is a token. That is easy, but the vocabulary then has to hold every form of every word. "Walk", "walks", "walked" and "walking" each need an entry, and so do names, typing mistakes and technical terms. A word that is missing from the vocabulary is called out-of-vocabulary, and a tokenizer with no entry for it cannot write it down.

Byte-pair encoding, or BPE, takes another route. It starts from the smallest tokens, single bytes, and counts which two neighbouring tokens occur together most often. It glues that pair into one new token and adds it to the vocabulary. Then it counts again and repeats. The idea comes from a data-compression method that replaces the most common pair of bytes with a byte that was not used in the data <Cite n={[9, 10]} />. The encoding itself needs no knowledge of any language.

A third idea is to cut words into morphemes, the smallest parts of a word that carry meaning. The word "unhelpful", for example, is un + help + ful, three parts that each mean something. It sounds ideal, but getting a program to find morphemes is hard. It needs knowledge of each language and its many exceptions, and finding them automatically is a research problem of its own. One family of methods, called Morfessor, learns a list of word segments from raw text without labelled examples <Cite n={11} />. A tokenizer that only counts, as BPE does, needs none of that knowledge. It is much simpler to build, and for many applications that is the practical choice. The price is that the tokens BPE finds often differ from morphemes, and one study argues that, for training language models, this makes BPE suboptimal <Cite n={12} />.

## What the step by step example showed

At every merge the example counted all the neighbouring pairs and joined the most common one. The first winner, `a + t`, was seen <Fact of="firstPairCount" /> times, and the new token got the next free id, <Fact of="firstNewId" />.

Sometimes several pairs are tied for the most common. Our rule is: the pair with the smaller numeric values win. The code published by the author of the BPE-for-translation method settles ties differently: among the tied pairs it takes the one that sorts last as text <Cite n={13} />.

Merging does not go on forever. We chose in advance to stop after <Fact of="merges" /> merges. Every merge adds exactly one entry, so the vocabulary ended with <Fact of="byteValues" /> + <Fact of="merges" /> = <Fact of="vocabularySize" /> entries. This is how the method is defined: the final vocabulary is the starting set of symbols plus the number of merges, and that number is the only setting of the algorithm <Cite n={[10, 7]} />. The text, meanwhile, shrank from <Fact of="startPieces" /> tokens to <Fact of="endPieces" />.

That is the trade-off. A bigger vocabulary makes the text shorter, but the list grows, and many of its entries are rare tokens that are used far less often than the common ones <Cite n={14} />. A smaller vocabulary keeps the list small but leaves the text long, and the best size depends on how big the model is <Cite n={15} />.

What about a word the tokenizer never saw? In the example, the word "that" was built from tokens already in the vocabulary, and the cat emoji, which has no learned token, fell back to its raw bytes. That works because the vocabulary always holds every single byte: a byte-level version of BPE only needs a base vocabulary of <Fact of="byteValues" /> entries <Cite n={16} />, and it can write any text <Cite n={17} />. So with byte-level BPE no word is out-of-vocabulary. An unfamiliar word is simply cut into more, smaller tokens.

## The tokenizer behind the demos

The examples below use the same tokenizer algorithm as the step by step example above, but it is trained on a small corpus of English text. It is a tiny toy, but it works the same way as the real tokenizers used in popular models. Real tokenizers follow the same steps, but their vocabularies are far bigger, so their splits will differ from the ones you see here. Many popular models use byte-pair encoding, though not all do.

Compared with the tiny toy in the step by step example, real tokenizers differ in three ways. They learn from a huge amount of text, not from one sentence. They split text with a rule before merging, so tokens do not run across spaces and punctuation. And their vocabularies hold tens of thousands of tokens or more.

The tokenizer of GPT-2 has 50,257 entries <Cite n={[16, 18]} />. The tokenizer of GPT-4 has 100,257 <Cite n={[18, 19]} />, and the one of GPT-4o has 200,019 <Cite n={[18, 19]} />.

## What you just saw

Three things are worth remembering from your experiments.

- Spaces belong to tokens. A word with a space in front of it is often a single token.
- Rare words split into several tokens, while many everyday words stay whole.
- Some characters, such as emoji, are too big for one token. An emoji takes several bytes, and the tokenizer can cut between them. That is why hatched chips appear, and why you never see a garbled symbol: a token that holds only part of a character is shown as its raw bytes instead. Hatched chips inside one frame are the bytes of a single character, which is shown in front of them. For example, the character [男](https://en.wiktionary.org/wiki/%E7%94%B7) is stored as the bytes `E7 94 B7`, and the tokenizer may cut between them.
