## How does a computer store text?

A _character_ is a single letter, digit, space or punctuation mark. A computer does not store characters as shapes. It stores each one as a number, using a table that says which number belongs to which character. Such a table is called a character encoding.

A byte can store <Fact of="byteValues" /> different values: 0 to <Fact of="lastByteValue" />. Most English letters take up one byte, other characters may take several. The difference comes from history.

The first widely used encoding was ASCII, published in the United States in 1963 [@asciiEthw]. It had room for 128 characters, which was enough for English letters, digits and punctuation, plus a few control codes such as line ends and carriage returns [@asciiEthw]. Every ASCII character fit in a single byte, with room to spare.

Computers soon used that spare room for more characters, such as accented letters. But every country and every company filled it differently, so the same value could mean different letters on different machines, and text arrived garbled. Languages such as Japanese and Chinese, with thousands of characters, needed several bytes for each one and ended up with encodings of their own, which did not agree with each other either [@mojibake].

In 1987, engineers at Apple and Xerox began the Unicode project, which aimed to give every character in every language its own unique number [@unicodeHistory]. Unicode decides the number, and UTF-8 defines how to store that number as bytes. UTF-8 keeps the ASCII values exactly as they were and uses between one and four bytes for every other character [@rfc3629]. Today, over 99% of the websites whose encoding is known use UTF-8 [@w3techs].

For example, in ASCII and UTF-8 alike, the letter _t_ has the value <Fact of="byteOfT" />, and a space is <Fact of="byteOfSpace" />.

Here is the opening line of *Anna Karenina*, by Leo Tolstoy (translation by Constance Garnett [@karenina]):

> Happy families are all alike; every unhappy family is unhappy in its own way.

To the computer, the sentence is a row of byte values, each between 0 and <Fact of="lastByteValue" />. The space has a value too, because a space is a character like any other.

## What is a language model, and why numbers?

Natural language processing, or NLP, is the field of computer science whose goal is to get computers to perform useful tasks involving human language. A language model is a computational system that can predict the next word from previous words [@jurafskySlp3]. A language model is the kind of AI program behind chat assistants.

Inside, a language model is built from arithmetic. It multiplies and adds numbers, and letters cannot be added up, so text has to become numbers before the model can use it.

The number a model receives for a piece of text is a label, not an amount. The letter _t_ having a bigger value than the letter _a_ does not make it more important. The value only says which character it is.

## Why not feed in raw bytes?

The simplest choice is to give the model the bytes themselves. The model then needs only a list of the pieces it can read, called its **vocabulary**, and that list holds just <Fact of="byteValues" /> entries, one for each possible byte. Every text in every language can be written this way.

As many other terms in computer science, "vocabulary" is an analogy. It does not mean the words a person knows. It means the fixed list of entries a model can read and write, and an entry does not have to be a word.

The problem is length. Take the sentence "the cat sat on the mat and the cat sat on the hat". It has <Fact of="wordCount" /> words but <Fact of="startPieces" /> bytes. A model that reads raw bytes has to work through sequences that are longer than the same text cut into words, which costs more computation [@xueByt5].

## Why not whole words?

The opposite choice is to cut text at spaces, so that every word gets its own entry in the vocabulary. That is easy, but the vocabulary then has to hold every form of every word. "Walk", "walks", "walked" and "walking" each need an entry, and so do names, typing mistakes and technical terms. A word that is missing from the vocabulary is called out-of-vocabulary, and a model with no entry for it cannot write it down.

There is a deeper problem. Not every language is written with spaces between words. In Chinese, Japanese, Thai and Lao, for example, reliably finding where one word ends takes a dictionary or similar tools, not a simple cut at spaces [@unicodeTr29]. A list of whole words would first need a way to find the words, and that differs from language to language. A language model that should handle text in any language cannot lean on spaces.

## Why not cut words into meaningful parts?

A third idea is to cut words into morphemes, the smallest parts of a word that carry meaning. The word "unhelpful", for example, is "un" + "help" + "ful", three parts that each mean something. It sounds ideal, but getting a program to find morphemes is hard.

Languages build words in very different ways. English adds a few endings, as in "walk", "walks", "walked" and "walking". Basque is called an agglutinative language, because it keeps attaching endings, one after another, to the same word [@aduriz2000]. A single Basque noun can take at least 135 different forms, and one word can say what takes a whole phrase in English: "amarengan" is "ama" (mother) + "aren" (of the) + "gan" (on), which together mean "on the mother" [@aduriz2000]. A program that had to cut every word into its meaningful parts would have to learn all of these endings for every language. Then the instructions for marking morpheme boundaries by hand, written to work for any language, include details that are specific to each language [@mott2020]. Machine learning approaches struggle as well: in one study, for the two languages with very little data, the best model was right less than half of the time [@mager2020]. Finding morphemes automatically is a research problem of its own [@creutz2007].

## A practical compromise: tokens

Engineers took a practical way out. Bytes make the text too long, whole words need a very long list and a way to find them, and morphemes are hard to find. So they settle for something in between that works well enough. Let the vocabulary hold two kinds of entries. The first kind is single bytes, so that any text can still be written. The second kind is longer pieces of text that turn up often, such as "the", "ing" or "cat". Text made of common pieces then needs few entries, and rare text falls back on smaller ones. Each piece in the vocabulary is called a **token**. A token is a small piece of text that a language model reads and writes. It can be a whole word, part of a word, a single character, a space plus a word, a piece of punctuation, etc.

A program called a tokenizer cuts text into tokens from the vocabulary and turns them into numbers, called indices or ids (short for identifiers). It can also turn the ids back into text.

Byte-pair encoding, or BPE, is one popular way to build such a vocabulary. It starts from the smallest tokens: single bytes, and counts which two neighbouring tokens occur together most often. It glues that pair into one new token and adds it to the vocabulary. Then it counts again and repeats. The idea comes from a data-compression method that replaces the most common pair of bytes with a byte that was not used in the original data [@gage1994; @sennrich2016]. The encoding itself needs no knowledge of any language.

BPE is an engineering answer, not a linguistic one. It only counts, so it does not look for morphemes and needs none of the language knowledge that finding them takes. It is much simpler to build, and for many applications that is the practical choice. In the translation study that adapted it, the pieces it found worked better than looking unknown words up in a dictionary [@sennrich2016]. The price is that the tokens BPE finds often differ from morphemes, and one study argues that, for training language models, this makes BPE suboptimal [@bostrom2020].

## Tokens are not words

Tokens are not the same thing as words. The same sentence can contain more tokens than words.

## How the numbers are assigned

The vocabulary is a numbered list, and the id of a token is its position in the list. Counting starts at 0, so a vocabulary of V entries uses the ids 0 to V - 1.

The demo below gives its starting symbols the ids of their byte values, and every new token is added at the end of the list with the next id. So the letter _t_ gets the id <Fact of="byteOfT" />. Similarly to character encodings, these ids are only labels in a list. A bigger number does not mean a rarer or more important word, and a different tokenizer can give the same token a different id. For example, the tokenizer of GPT-2, used later in this post, gives the letter _t_ the id <Fact of="gpt2IdOfT" />.

## What the step by step example showed

At every merge the example counted all the neighbouring pairs and joined the most common one. The first winner, `a + t`, was seen <Fact of="firstPairCount" /> times, and the new token got the next free id, <Fact of="firstNewId" />.

Sometimes several pairs are tied for the most common. Our rule is: the pair with the smaller numeric values win. The code published by the author of the BPE-for-translation method settles ties differently: among the tied pairs it takes the one that sorts last as text [@subwordNmt].

Merging does not go on forever. We chose in advance to stop after <Fact of="merges" /> merges. Every merge adds exactly one entry, so the vocabulary ended with <Fact of="byteValues" /> + <Fact of="merges" /> = <Fact of="vocabularySize" /> entries. This is how the method is defined: the final vocabulary is the starting set of symbols plus the number of merges, and that number is the only setting of the algorithm [@jurafskySlp3; @sennrich2016]. The text, meanwhile, shrank from <Fact of="startPieces" /> tokens to <Fact of="endPieces" />.

That is the trade-off. A bigger vocabulary makes the text shorter, but the vocabulary grows, and many of its entries are rare tokens that are used far less often than the common ones [@gowda2020]. A smaller vocabulary keeps the list small but leaves the text long, and the best size depends on how big the model is [@tao2024].

What about a word the tokenizer never saw? In the example, the word "that" was built from tokens already in the vocabulary, and the cat emoji, which has no learned token, fell back to its raw bytes. That works because the vocabulary always holds every single byte: a byte-level version of BPE only needs a base vocabulary of <Fact of="byteValues" /> entries [@radford2019], and it can write any text [@wang2020]. So with byte-level BPE no word is out-of-vocabulary. An unfamiliar word is simply cut into more, smaller tokens.

## A real tokenizer: GPT-2

The examples below use the real tokenizer of GPT-2, a language model that OpenAI published in 2019 [@radford2019]. It uses the same BPE algorithm as the miniature example, but it learned from a huge amount of text from web pages [@radford2019]. Many popular models use byte-pair encoding, though not all do.

Compared with the step by step example, real tokenizers differ in three ways. They learn from a huge amount of text, not from one sentence. They split text with a larger set of rules before merging, so tokens do not run across spaces and punctuation. And their vocabularies hold tens of thousands of tokens or more.

The tokenizer of GPT-2 has 50,257 vocabulary entries [@radford2019; @tiktokenPublic]. The tokenizer of GPT-4 has 100,277 [@tiktokenPublic; @tiktokenModel], and the one of GPT-4o has 200,019 [@tiktokenPublic; @tiktokenModel].

GPT-2 is an older tokenizer. I chose it because its tokenizer file is only about <Fact of="gpt2FileMb" /> megabytes, because it is released under a permissive licence [@gpt2License], and because its design is published openly [@radford2019]. Newer models cut text differently. For example, GPT-2's rule for splitting text before merging keeps a whole run of digits together, while the tokenizer of GPT-4 cuts a run of digits into short groups [@tiktokenPublic; @tiktokenModel].

Three things are worth remembering from this demo:

- Spaces can belong to tokens. A word with a space in front of it is often a single token.
- Rare words split into several tokens, while many everyday words stay whole.
- Some characters, such as emoji, are too big for one token. An emoji takes several bytes, and the tokenizer can cut between them. For example, the character [男](https://en.wiktionary.org/wiki/%E7%94%B7) is stored as the bytes `E7 94 B7`, and the tokenizer may cut between them.

## How does GPT-2 compare with other models?

GPT-2 is one way to cut text into tokens. Here it sits next to BERT, a model of about the same age that uses a different method. Pick a text, or type your own, and you can see where each one cuts. BERT uses a method called WordPiece. Unlike GPT-2, it does not work on bytes: its vocabulary holds only the characters and word pieces it was built with [@hfWordpiece]. A word it cannot build from that vocabulary is replaced by one special token, `[UNK]`, short for "unknown", which stands in for the whole sequence and hides what it said [@hfWordpiece]. A token like this is "special" because it is not a piece of text but a signal to the model. If you are curious about BERT, its documentation is a good place to start [@hfBert].
