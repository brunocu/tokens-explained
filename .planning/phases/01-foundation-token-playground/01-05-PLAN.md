    1. Create `src/core/chars.ts`. Pure TypeScript, no DOM, no framework, explicit `.ts` import specifiers, `import type { Token } from "./types.ts"` only. It works on bytes only (PITFALLS.md pitfall 2) and uses no platform decoder: the code point of a valid sequence is computed arithmetically from its bytes. Export the types and functions listed in the interfaces block of this plan (this task implements `groupBytes`, `layoutChips` and `labelFor`; the other two functions arrive in Tasks 2 and 3). Behaviour of `groupBytes(tokens)`:
       a. Join all token bytes into one stream, remembering for every stream byte which token it came from and each token's start offset.
       b. Walk the stream with the standard UTF-8 rules (UI-SPEC "How bytes are grouped", step 2, the same rules as the WHATWG decoder). A byte 00 to 7F is a single-byte character. A lead byte C2 to DF needs 1 continuation byte, E0 to EF needs 2, F0 to F4 needs 3; continuation bytes are 80 to BF, except that the first continuation byte must be A0 to BF after E0, 80 to 9F after ED, 90 to BF after F0 and 80 to 8F after F4. A byte that is not a valid lead, or whose sequence fails (wrong or missing continuation, or the stream ends first), is one invalid character of length 1 and the walk resumes at the very next byte, so the bytes after a failed lead are examined on their own (a stray 80 to BF byte is invalid).
       c. Produce one `CharInfo` per character: start, end, length, kind (single, multi or invalid), codePoint (computed from the bytes, null for invalid), label (from `labelFor`), firstToken and lastToken (the token indices holding its first and last byte).
       d. Produce one `TokenGroups` per token: `pieces` lists, in order, every non-single-byte character that has at least one byte in the token, with the token-local `from` and `to` (to exclusive) and the 1-based byte numbers `first` and `last` within the character; `partial` copies `token.isPartial`; `frame` is set in step e.
       e. Frames (UI-SPEC "Character frame"). A character is split when its firstToken differs from its lastToken. Two consecutive tokens are linked when some split character has bytes in both. A token is framed when it holds a piece of a split character or an invalid piece. A frame is a maximal run of consecutive framed tokens in which every consecutive pair is linked; a framed token linked to no neighbour (it holds only invalid bytes) is a frame of its own. Each `Frame` records `first` and `last` token indices, `labels` (the labels of the split characters whose tokens lie in the frame, in stream order) and `invalid` (true, with the single label `invalid`, when the frame has no split character; see PD-04 above). Set `TokenGroups.frame` to the frame index for every token inside a frame, null otherwise.
       f. `labelFor(kind, codePoint)`: for this task, an invalid character gives the name-style label `invalid`, U+FFFD gives the name-style label `placeholder`, every other character gives the character itself (built with `String.fromCodePoint`) in char style. Task 2 completes the table behind this same function.
       g. `layoutChips(grouping)` returns the render order: scanning token indices upwards, a token that starts a frame yields one `frame` item holding all the token indices of that frame (and the scan jumps past the frame), every other token yields one `chip` item. Every token index appears exactly once.
       `groupBytes([])` returns empty lists. Satisfy `noUncheckedIndexedAccess`.
