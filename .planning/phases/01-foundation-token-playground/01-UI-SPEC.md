- Sans stack (no download): `--font-sans: system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`.

- Glyph coverage gate (executor must verify in a browser, not assume): `␣`, `↵`, `⇥` must render as visible glyphs in Chrome, Safari (iOS) and Firefox. Render them in a dedicated `.ws` span using the sans stack plus `"Segoe UI Symbol", "Apple Symbols", "DejaVu Sans"` as fallbacks, because the latin subset of the mono font may not include them. If `␣` fails to render on any of these, fall back to `·` (U+00B7) for space and update the legend text to match.

Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between token chips (both axes), icon/glyph gaps, chip vertical padding |
| sm | 8px | Chip horizontal padding, gap between buttons in a row, label-to-control gap |
| md | 16px | Default element spacing, page side padding below 640px, card padding below 640px |
| lg | 24px | Page side padding at 640px and above, card padding at 640px and above, paragraph spacing |
| xl | 32px | Gap between playground sub-blocks (controls, counts, token display) |
| 2xl | 48px | Space above each H2, site header height |
| 3xl | 64px | Space above the post title, space below the post end |

Exceptions (not part of the spacing scale, listed so the executor does not "fix" them):

- Border widths: chip outline 2px, card and input border 1px, focus ring 2px with 2px offset.
- Interactive targets: every button, segmented option, toggle and the `<details>` summary has `min-height: 44px` and `min-width: 44px` (exceeds the WCAG 2.2 2.5.8 minimum of 24px).
- Reading column measure: `max-width: 680px` (a measure, not a spacing value). The playground card uses the same column width.
- Textarea `min-height: 128px`, `max-height: 320px`, vertical resize only.
- Chip `min-height: 32px` (visual size; chips are not interactive).
- Line-height values are unitless ratios and are not spacing tokens.
- R-01 character frame: outline 2px solid (dotted for invalid bytes), label-cell divider 2px solid, dashed token dividers 2px, byte-line underline 2px. Label cell padding 4px 8px (xs, sm). Gap between byte groups in a byte line 8px (sm). No new spacing values.

### Token chip palette (the project's main visual accent, per D-13)

Chip `i` uses palette entry `i mod 4`, in token order. The palette alternates on top of the outline, so boundaries never depend on color alone (D-05, FOUND-02). Chip text color is the Text color of the theme.

| Entry | Light fill | Light outline | Dark fill | Dark outline | Hue family |
|-------|------------|---------------|-----------|--------------|------------|
| 0 | `#CFE3FF` | `#3366B3` | `#1F3A5F` | `#7FB0F0` | Blue |
| 1 | `#FFD9B8` | `#B35C14` | `#5A3515` | `#E0954F` | Orange |
| 2 | `#CDEFD2` | `#2F7A3B` | `#1E4A2A` | `#6CC27C` | Green |
| 3 | `#E6D4FA` | `#7A4BB3` | `#46306B` | `#B794E8` | Purple |

Measured contrast: chip text on fill 12.6:1 to 14.0:1 (light), 8.6:1 to 9.7:1 (dark). Outline on secondary surface 4.3:1 to 5.5:1 (light), 6.7:1 to 7.7:1 (dark), all above the 3:1 non-text minimum. Blue/orange/green/purple differ in lightness as well as hue; the executor must still run a color-blindness simulation (deuteranopia, protanopia, tritanopia) in the Phase 1 verification, but color is never the only boundary cue.

Whitespace glyph color inside chips: `#5C5C5C` (light, at least 4.8:1 on every fill) and `#BDBDBD` (dark, at least 5.4:1 on every fill).

Partial-character chip (neutral, ignores the alternating palette):
- Light: fill `#E9E7E1`, 2px dashed outline `#6B6B6B`, diagonal hatch overlay (`repeating-linear-gradient(45deg, transparent 0 4px, rgba(0,0,0,0.08) 4px 5px)`), text `#1A1A1A`.
- Dark: fill `#2A2A2A`, 2px dashed outline `#9A9A9A`, hatch overlay with `rgba(255,255,255,0.10)`, text `#ECECEC`.
- Dashed outline plus hatch means "this is a piece of a character, not a text token" without relying on color.

Character frame and label (R-01). No new hex values. Two alias custom properties are added to `tokens.css` so the intent is named: `--char-frame: var(--text)` and `--char-label-bg: var(--bg)`.
- Light: frame outline `#1A1A1A` (15.8:1 on Secondary `#F5F4F0`), label cell fill `#FFFFFF`, label text `#1A1A1A` (17.4:1), name-label text `#5C5C5C` (6.7:1 on `#FFFFFF`).
- Dark: frame outline `#ECECEC` (14.1:1 on Secondary `#1E1E1E`), label cell fill `#121212`, label text `#ECECEC` (15.9:1), name-label text `#A8A8A8` (7.9:1 on `#121212`).
- Dashed token dividers inside a frame reuse `--partial-line` (4.3:1 on the light partial fill, 5.1:1 on the dark partial fill, above the 3:1 non-text minimum).
- The frame is the strongest-contrast outline on the page on purpose: it carries the one fact R-01 adds. It is never accent-colored.
- Ratios computed with WCAG relative luminance on 2026-10-05.

Print: set `print-color-adjust: exact` on chips and keep the 2px outline so boundaries survive when backgrounds are dropped.

## Playground Contract (island: `Playground.svelte`)

Hydrate with `client:visible`. The island is server-rendered, so the default text, its chips, counts and table are present as static HTML before hydration (works with JavaScript disabled or slow). All browser-only work happens in `onMount`. A `<noscript>` note inside the card reads: "Typing needs JavaScript. The example below shows the default text."

The toy tokenizer and its fixed merge list ship inside the page bundle (a few hundred merges, D-01); the tokenizer itself makes no network request. The island's own script is loaded asynchronously (`client:visible`), so the card has explicit loading and failed-load states. A reader is never left with controls that look usable but do nothing.

Island lifecycle states (the card root carries `data-state="loading" | "ready" | "failed"`; server-rendered value is `loading`):
- **Loading** (server render until `onMount` runs): textarea is `readonly`, example buttons, Reset text, segmented control and peek toggle carry the `disabled` attribute with a visibly dimmed style (still meeting the 3:1 non-text contrast for the control border), and a status line directly under the card heading (Label size, Muted, `role="status"`) reads the "Loading" copy below. The default chips, counts and table stay visible as static HTML. No spinner or animation. `onMount` flips the state to `ready`, removes the status line, enables the controls and does not move focus.
- **Failed to load** (the island script never hydrates, for example a dropped connection): because the island uses `client:visible`, it does not hydrate until the card nears the viewport, so the timer must not start at page load. A tiny inline script in the layout watches the card with an `IntersectionObserver` (same `rootMargin` Astro uses for `client:visible`, default 0px) and, 8 seconds after the card first enters the viewport, sets `data-state` to `failed` if it is still `loading`. A reader who has not scrolled to the card yet never sees the failure message; they see only the loading status line (static chips already visible). The status line then shows the "Failed to load" copy in the Error color with a "Reload page" text button (native `<button>`, `location.reload()`, `min-height: 44px`). Controls stay disabled and the static default chips stay visible. If the island hydrates later, `onMount` sets `ready` and clears the message.
- **No JavaScript**: `<noscript>` shows the no-JS note and hides the loading status line (via a `<noscript><style>` rule), so a reader without JS is never told something is still loading.
- **Ready**: everything below applies. An unexpected tokenizer exception while ready is the separate runtime error state (Copywriting Contract, "unexpected failure").

Vertical order inside the card, top to bottom, `gap: 32px (xl)` between blocks:

1. **Text input block**
   - Visible `<label>`: "Your text" (Label size, weight 600), 8px above the textarea.
   - `<textarea>`: mono 18px, `min-height: 128px`, 1px Control border, 4px radius, 16px padding, background Dominant. Attributes: `autocapitalize="off" autocorrect="off" spellcheck="false" dir="auto" maxlength="1000"`. Tokenization pauses between `compositionstart` and `compositionend` (IME, Pitfall 23).
   - Below it (Label size, Muted): "Your text stays in your browser. Nothing is sent anywhere." (must be true; no analytics on input).
   - Limit message (only at 1,000 characters, Error color, `role="status"`): "That is the limit for this playground: 1,000 characters. Delete some text to keep typing."
2. **Examples and reset block**
   - Label "Try an example" (Label, weight 600), then a wrapping row of five example buttons (`gap: 8px`) and a sixth text button (Reset).
   - Example buttons (secondary style: transparent fill, 1px Control border, 8px horizontal padding 16px, Label size, `min-height: 44px`), with the exact text each one loads (D-07):
     | Button label | Loads |
     |--------------|-------|
     | A rare long word | `The word floccinaucinihilipilification is almost never used.` |
     | Numbers and dates | `On 2026-10-03 I paid $1,234.56 for 3 tickets.` |
     | An emoji | `Great job 🎉 see you soon 🙂` (party popper U+1F389, slightly smiling face U+1F642; each is a 4-byte character and must produce hatched partial chips unless the toy has a merge for it, which D-02 says it does not) |
     | A line of classic literature | `It is a truth universally acknowledged, that a single man in possession of a good fortune, must be in want of a wife.` (Jane Austen, Pride and Prejudice, 1813, public domain) |
     | A non-English line | `男女 こんにちは` (R-01, user decision 2026-10-05; adjacent multi-byte characters so the reader sees one character frame per character: 男 and 女 are 3 bytes each, each hiragana is 3 bytes) |
   - "Reset text" (text-style button, accent not used, underline on hover/focus) restores the default text and moves focus to the textarea. No confirmation dialog: the action only replaces a short scratch text, so it is not treated as destructive.
   - Choosing an example replaces the textarea content, keeps the current view toggles, and moves focus to the textarea with the caret at the end.
   - Default text **(default)**: `Tokenization splits unusual words into pieces, but common words stay whole.` Acceptance check at implementation time: with the shipped merge list, the default must produce at least one word that splits into two or more tokens, at least one token with a leading-space glyph, and at least one common word that is a single token. If it does not, change the sentence, not the contract.
3. **View controls block** (one wrapping row, `gap: 16px`)
   - Segmented control "Show": two native radio inputs styled as a joined pair, legend "Show", options "Token text" (default) and "Token IDs" (D-08). Selected option uses the accent fill. Arrow keys move between options, Space/Enter selects. Each option `min-height: 44px`.
   - Toggle "Peek under the hood" (native `<input type="checkbox">` styled as a switch with a visible text label and visible on/off state, D-04). Default off. Helper text next to it (Label, Muted): "Show the raw bytes behind every token."
4. **Counts block**: three stat items in a row (Heading size number in sans weight 600, Label size label in Muted below): "Tokens", "Characters", "Words", always visible (D-09, TOK-02). Counting rules: characters are visible characters counted with `Intl.Segmenter` at grapheme granularity (an emoji or accented letter counts as 1); words are `Intl.Segmenter` word-like segments; tokens are the number of tokens the toy produced (partial-character pieces each count as a token). One debounced (500ms) visually-hidden `role="status"` live region announces "{n} token(s), {c} character(s), {w} word(s)"; chips are never announced individually.
5. **Token display** (shared `TokenDisplay`, see next section) followed by the one-line legend and, when relevant, the split-character note and then the combined-character note (R-01).
6. **Table alternative**: a native `<details>` whose `<summary>` reads "View tokens as a table" (Label, weight 600, `min-height: 44px`), placed directly after the legend. Closed by default, open state preserved while typing.

## Token Display Contract (shared component: `TokenDisplay.svelte`)

Reused unchanged by Phases 2-4. Props: an array of tokens, each carrying `bytes` (Uint8Array), `isPartial` (boolean), `id` (number), plus a display mode (`text` or `ids`) and `showBytes` (boolean). Tokens are never stored or compared as decoded strings (Pitfall 2). A replacement character U+FFFD must never appear in the output (success criterion 4); partial tokens are rendered from bytes only.

Chip anatomy (D-05):
- `display: inline-flex`, flex-wrap row container with `gap: 4px` (xs) in both directions.
- Padding 4px 8px, `min-height: 32px`, 2px solid outline (palette entry outline color), 4px corner radius, fill from the palette entry. Mono 18px text, `white-space: pre`, `unicode-bidi: isolate`, `max-width: 100%`, `overflow-wrap: anywhere` so a very long token wraps instead of breaking the layout on a 360px screen (Pitfall 22).
- Chips are not focusable and not in the tab order. Hover and focus do nothing (no hover-only tooltips, Pitfall 13); everything a chip can show is also visible in the chip or in the table alternative.
- The chip container is `aria-hidden="true"`. Its content is represented by the table alternative and the live region.

Whitespace (D-06, FOUND-03): inside a chip, a space is shown as `␣`, a newline as `↵`, a tab as `⇥`, in the whitespace glyph color, in a `.ws` span. A token that is only whitespace shows only glyphs. A chip that contains a newline is followed by a forced line break in the chip flow, so lines of the input read as lines of chips. Legend (one line, Label size, Muted, directly under the chips): "␣ space   ↵ new line   ⇥ tab   Hatched chips are raw bytes. Hatched chips in the same frame make up one character, which is shown in front of them." (R-01 replaces the 2026-10-03 fourth item, "Hatched chips are pieces of one character, shown as raw bytes."). The legend is always visible and wraps at narrow widths.

Content by mode and chip type:

| Chip type | "Token text" mode | "Token IDs" mode | "Peek under the hood" on |
|-----------|-------------------|------------------|--------------------------|
| Normal text token | token text with whitespace glyphs | numeric ID (mono 18px) | adds a second line of bytes in uppercase hex, e.g. `48 65 6C` (mono 14px, Muted) |
| Partial-character token | bytes in uppercase hex, e.g. `F0 9F` (mono 14px), hatched dashed chip, always inside a character frame (see R-01 section) | numeric ID on line one, hex bytes on line two (mono 14px), still inside the frame | no change in text mode (bytes already shown); in IDs mode unchanged |

Bytes are shown by default only on partial chips (D-04). Switching mode or the peek toggle never re-animates chips.

Split-character note (shown only when at least one character is split across tokens; Label size, Muted, below the legend; `role="status"` merged into the same debounced live region): "1 character was split across several tokens. Each hatched chip holds a piece of it." / "{n} characters were split across several tokens. Each hatched chip holds a piece of them." Plain-language reason for the post, not the UI: some characters take more than one byte, and this tokenizer works on bytes (FOUND-07).

Table alternative (inside the `<details>`, FOUND-04): a real `<table>` with `<caption>` "Tokens in your text", header cells `scope="col"`: "#", "Token", "ID", "Bytes". One row per token. The Token cell shows the text with whitespace glyphs (same as chip) or, for partial tokens, the R-01 wording "Byte {i} of {n} of {label}" (exact forms in the R-01 section; the 2026-10-03 text "Part of a character" is retired). Bytes cell shows uppercase hex. Label size, header row on Secondary surface with weight 600, 1px row dividers in Control border color, cells padded 8px 16px, table scrolls horizontally inside its own wrapper if it must (`overflow-x: auto`, wrapper is focusable with `tabindex="0"` and a label "Token table, scrollable"). The table always reflects the current text, mode independent.

Pre-split display: no pre-split boundaries are shown in the chips (chips show final tokens). The post explains the pipeline (text, pre-split, bytes, merges) in prose; Phase 2's stepper visualizes it.

## Byte-to-Character Grouping Contract (revision R-01, 2026-10-05)

User decision (verbatim intent): for multi-byte characters, show which bytes belong to each character. When several multi-byte characters sit together, for example in a foreign script, it is impossible to tell where one character starts and ends. Example: the kanji 男 is the bytes E7 94 B7.

Grounded in the built code (`src/core/toy.ts`, `src/components/TokenDisplay.svelte`): the toy's merges are ASCII-only (D-02), so every byte of a non-ASCII character is its own hatched partial chip, and all partial chips look identical (they ignore the alternating palette). `日本語` renders as nine identical hatched chips `E6 97 A5 E6 9C AC E8 AA 9E` with nothing showing that three bytes make one character. The same applies to a character whose bytes are split across token boundaries (every non-ASCII character today) and, in later phases, to real tokenizers that cut a character mid-way.

### Decisions

| Question | Decision | Why |
|----------|----------|-----|
| Placement | Inline, in the chip row itself: a **character frame** drawn around the hatched chips of one character, with the character shown in front of them. Not a separate strip, not hover or selection. | The reader is already looking at the chips. A separate strip makes them match bytes across two places by counting. Hover or selection breaks the no-hover-only rule (Pitfall 13) and does nothing on touch screens. A frame adds no height, wraps cleanly and keeps the 1 chip = 1 token structure. |
| Unit that is grouped | One Unicode character (one code point), because that is the unit UTF-8 turns into 1 to 4 bytes. This differs from the "Characters" count, which counts what the reader sees (graphemes). A visible symbol built from several code points gets one frame per part, plus an explanatory note (see Copy). **(default)** | Matches how the bytes are actually produced. Grouping by visible symbol would hide the 3-byte structure the reader is asking about. |
| Visual encoding | Shape and text, never color: a solid 2px outline around the group, a label cell with the character at the front, and dashed dividers marking where the tokenizer cut between bytes. | Boundaries must not depend on color (FOUND-02). Survives print, forced-colors and color-blindness. |
| When it shows | Always, for every partial chip (bytes are already shown by default on those, D-04). Under "Peek under the hood" and in the table, the same grouping idea applies to hex byte lines (see Byte-line grouping). Independent of the "Token text / Token IDs" mode. | One rule: wherever bytes are shown, the bytes of one character are visibly kept together. |
| Interactivity | None. Frames and labels are not focusable, have no hover or tooltip. | Consistent with chips (Pitfall 13). The table carries the same information as text. |

### How bytes are grouped (pure logic, no DOM)

A pure function (suggested name `groupBytes(tokens)`, new module `src/core/chars.ts` or inside `display.ts`; unit-tested in Vitest) decides the grouping. It works on bytes only (Pitfall 2) and never produces U+FFFD.

1. Join all token bytes into one stream, remembering each token's start and end offsets.
2. Walk the stream with the standard UTF-8 rules (same as the WHATWG decoder): `00-7F` is a 1-byte character; lead `C2-DF` needs 1 continuation byte; `E0-EF` needs 2; `F0-F4` needs 3; continuation bytes are `80-BF`, with the usual second-byte limits (`E0` then `A0-BF`, `ED` then `80-9F`, `F0` then `90-BF`, `F4` then `80-8F`).
3. Any byte that cannot be placed (a stray continuation byte, `C0`, `C1`, `F5-FF`, a wrong continuation, a sequence cut off at the end of the stream) is an **invalid byte**, a character of length 1.
4. Output per character: its byte range, whether it is single-byte, multi-byte or invalid, and its label (see Labels). For each token: which characters have bytes in it, and which byte number (i of n) of each.
5. A **split character** is a multi-byte character whose bytes lie in two or more tokens. Because partial chips are by definition tokens whose bytes alone are not valid UTF-8, every partial chip is either part of a split character or contains an invalid byte.

### Character frame (the primary visual)

Build a frame around each maximal run of consecutive chips that are linked by a split character (a character with bytes in both chip k and chip k+1 links them). In the toy tokenizer a run is always the 2 to 4 single-byte chips of one character.

- Markup: a wrapper (`data-char-frame`) containing a label cell (`data-char-label`) followed by the chips. The wrapper is one flex item of `.chips`, so it wraps to the next line as a whole and never breaks in the middle. **Each token still renders exactly one `[data-chip]` element; the wrapper and the label cell are not chips and carry no `data-chip` attribute** (existing tests count `[data-chip]`).
- Frame: `display: inline-flex; flex-wrap: nowrap; min-width: 0; max-width: 100%`, `border: 2px solid var(--char-frame)`, radius 4px, `overflow: hidden`, `direction: ltr` (so the label stays on the left even when the typed text is right-to-left).
- Label cell: shown first (left), `padding: 4px 8px`, `min-width: 32px`, fill `var(--char-label-bg)`, `border-right: 2px solid var(--char-frame)`, content centered both ways, `unicode-bidi: isolate`, `white-space: pre`. It holds the character at 18px (see Labels for characters that cannot be shown as themselves).
- Chips inside the frame keep the hatched look, hex text and (in IDs mode) their ID line. The frame replaces their individual outlines: first chip after the label has no left border, each later chip has `border-left: 2px dashed var(--partial-line)` as the **token cut mark**, no other borders, radius 0. A reader can still count tokens (one dashed divider per cut), and the solid outer frame says "this is one character".
- Palette: chips inside frames keep the hatched neutral fill. They still consume the alternating palette index by token position, so the color of the next normal chip does not change.
- Row height: a row that contains a frame is 4px taller than a row without one (the 2px frame border). Normal chips in that row stretch to match; this is intended and is not a bug.
- Invalid bytes: the frame uses `border-style: dotted` and the label reads "invalid" (name style). Only reachable from non-toy input (JavaScript strings always encode to valid UTF-8), but the component must handle it.
- A frame labels the characters that cross a chip boundary inside it, in order. In the toy this is always exactly one. For tokenizers whose chips can contain several characters (Phase 3), list up to 3 labels separated by a thin space, then "+{n} more".

Reference rendering (text mode, toy tokenizer), `男女` typed in the box:

```
[ 男 | E7 ┆ 94 ┆ B7 ]  [ 女 | E5 ┆ A5 ┆ B3 ]
```

`|` is the solid label divider, `┆` is a dashed token cut, the outer brackets are the solid frame, and the two spaces are the 4px gap. Two adjacent characters are two frames, so where one character ends and the next begins is always a solid frame edge plus a gap.

### Byte-line grouping (anywhere hex bytes are shown)

Applies to every hex line: partial chips, the extra line under "Peek under the hood", the second line in Token IDs mode.

- The bytes of a multi-byte character that has two or more of its bytes on that hex line are wrapped in one `.ch` group with `border-bottom: 2px solid currentColor` (one continuous underline from its first byte to its last, including the spaces between those bytes).
- Between two groups, and between a group and a neighbouring single-byte byte, leave an 8px gap with no underline, so the underline visibly breaks.
- A lone leftover byte of a split character (one byte on that line) is not underlined, because the frame already groups it.
- Single-byte (ASCII) bytes are never underlined, so a normal line such as `48 65 6C` is unchanged.
- Example, one chip holding two whole characters under Peek: `E6 97 A5` and `E6 9C AC` are two separate underlined groups with a gap between them, not a six-byte run. In the toy tokenizer this case does not occur (non-ASCII bytes are never merged), so today this rule is dormant; it is still built and unit-tested with synthetic tokens because `TokenDisplay` is shared with Phases 2-4.
- The table's Bytes column stays plain hex (one token per row); its Token cell carries the grouping in words.

### Responsive and accessibility

- A frame never breaks internally; it moves to the next line as a whole. Widest realistic frame (4-byte emoji, Token IDs mode, 3-digit IDs): label about 40px plus 4 chips of about 50px is 240px, which fits the 294px inner width of the card at 360px. As a safety valve, chips inside a frame use `min-width: 0` and `overflow-wrap: anywhere`, so an unexpectedly wide frame wraps its digits instead of causing a horizontal page scroll. Verified widths: 360px, 768px, 1280px.
- Color is never the only cue: solid outline, label with the character, dashed token cuts, hatch, and (for invalid) a dotted outline plus the word "invalid". Frames use borders (not background alone), so they survive forced-colors mode and print.
- The chip container stays `aria-hidden="true"`. The table's Token cell carries the grouping as text, so screen-reader users get "Byte 1 of 3 of 男" per row. Frames and labels are not focusable and not in the tab order.
- No motion is added. Frames appear and change instantly with the text, like chips.

### Implementation constraints (so Phases 2-4 can reuse it)

- `TokenDisplay` keeps its props (`tokens`, `mode`, `showBytes`, `splitCount`, `legend`, `emptyState`) and derives frames itself from `tokens[].bytes`; callers pass nothing new. The combined-character note needs the count of qualifying graphemes, so add one optional prop (suggested name `compositeCount`, default 0) beside `splitCount`, computed in the island from the same `groupBytes` result.
- The grouping function and the label table are pure TypeScript with Vitest golden cases: `男` (E7 94 B7), `男女`, `日本語`, 🎉 (F0 9F 8E 89), decomposed é, the family emoji, a flag, `EF BF BD`, a stray `94`, a truncated `E7 94` at the end, overlong `C0 80`, `ED A0 80`, `F5`, mixed `A5 20 74` (end of one character, then ASCII).
- Do not set `lang` on label cells (it would not help and could pick a wrong regional glyph variant); rely on the system font fallback.

- Contrast: text 4.5:1 minimum and non-text 3:1 minimum in both themes (measured values in Color).
- Screen readers: chip container is `aria-hidden="true"`; the `<table>` inside `<details>` is the text alternative; one debounced `role="status"` region announces counts; the textarea has `aria-describedby` pointing to the privacy line.
- Keyboard: every control is a native element (textarea, button, radio, checkbox, details/summary), reachable and operable without a mouse, with the tab order listed under Interaction. No keyboard traps, no hover-only information.
- Target size: at least 44x44 CSS px for all controls.
- Reduced motion: all transitions removed under `prefers-reduced-motion: reduce`.
- Language: `<html lang="en">`; headings form a strict outline (one H1, then H2, H3 not skipped); the playground card is a `<section aria-labelledby>` tied to its H2.
- Color scheme follows the OS; both themes verified with axe or Lighthouse and a manual keyboard pass as part of Phase 1 verification.
