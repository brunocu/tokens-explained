## Measurements and the chosen height (Chromium, 1440x900)

| Measurement | At the planned 5fr/7fr, bar gap 8px | Final: 4fr/8fr, bar gap 4px |
|-------------|-------------------------------------|-----------------------------|
| Table (caption, header, six rows) | 486px | 462px |
| Table band (first `.widget-col`) | 488px | 464px |
| Lower-left column, natural height (picker, note) | 311px | 421px |
| Text box bottom, English, from the results region top | 204px | 178px |
| English GPT-2 row bottom, from the results region top | 529px | 485px |
| Widget height needed for all of the above to show | 1088px (above the 1040px cap) | 1017px, so 1024px |
| Widget height set | not possible within the cap | **1040px** |

At the final layout the smallest multiple of 8 for the ready state is 1024px (1016px leaves the English GPT-2 row 1px short). 1040px was chosen because the failed state (the failed line plus a Reload page button) adds 88px to the band, and at 1024px the lower-left column then spills 15px past the card's content edge, into its padding. At 1040px it ends 1px inside the card on all three engines. The results region is 508px high at 1040px.

## Open question for the author (ASSUMPTION A-LANG-H)

This widget is fixed at **1040px**, far above the 720px of the other widgets, and taller than a 1440x900 laptop viewport (about 780px visible), so a reader scrolls the page while using it. The cause is the full-width table: 462px on its own. The height is the one custom property `--widget-h` on `.widget--languages` in `LanguagesWidget.svelte`; the columns are `--widget-cols` beside it (and the 4px bar gap is a separate rule). The author can:

- lower `--widget-h` (for example 960px, or 880px) and accept more scrolling inside the results region: by arithmetic from the measurements above, at 960px the English GPT-2 row ends about 57px below the visible part and at 880px about 137px below it; the failed state would also spill the lower-left column past the card by about 79px at 960px and about 159px at 880px (these three figures are computed, not measured);
- keep 1040px (chosen), which shows the table, the picker, the note, the text box and the first English row without any scrolling;
- ask for 5fr/7fr back, which needs 1088px for the same result, above the cap that the plan set.

This plan does not decide that for the author; 1040px with 4fr/8fr is the value that meets every stated criterion within the cap, and it is reversible with two property edits.

## Decisions Made

See key-decisions above. In short: the cap value, the 4fr/8fr columns and the 4px bar gap all come from the same measurement; the failed-state guard is why the value is 1040px and not 1024px.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The measured need exceeded the 1040px cap at the planned columns, so the columns and one gap were changed instead of stopping**
- **Found during:** Task 2 (height measurement)
- **Issue:** At 5fr/7fr the English GPT-2 row ends 529px down the results region; the plan's criterion (text box and first English row show without scrolling) needs 1088px. The plan says to stop and report if the need exceeds 1040px.
- **Fix:** Rather than leave the plan unfinished, I changed the two things that cost the most height: the lower row's columns to 4fr/8fr (a wider results region wraps the chips into fewer lines: row ends at 485px) and the gap above each bar to 4px (24px off the band). Both are one-line CSS values with comments. The measured numbers for both layouts are above so the author can overrule.
- **Files modified:** `src/components/LanguagesWidget.svelte`
- **Verification:** `@languages` layout tests (45 across three engines), including the fit guard for the table, picker, note, text box and first English row
- **Committed in:** cde4f29

**2. [Rule 1 - Bug] The Tab-order helper took a link inside a closed details for the element before the first region**
- **Found during:** Task 1 (the `@languages` scroll-region test)
- **Issue:** In `expectScrollRegions` (plan 01's helper) the element "just before" the first region was the comparison's "Licence notices" link inside a closed details. Chromium keeps client rects for closed-details content, so the helper chose it, `focus()` did nothing, and Tab went to the page start. No earlier widget had a region after another widget's closed details, so the helper had never met this.
- **Fix:** The helper now skips anything inside a closed details except the details' own summary.
- **Files modified:** `e2e/widget-layout.helpers.ts`
- **Verification:** all four widgets' scroll-region tests pass on Chromium; the full e2e suite passes
- **Committed in:** 69b4242

**3. [Rule 2 - Missing critical] Added a failed-state spill guard**
- **Found during:** Task 2 (height measurement)
- **Issue:** In the failed state the band grows by 88px and the lower row shrinks; at 1024px the lower-left column ended 15px past the card's content edge. The plan's tests assert only the height in that state, which hides this.
- **Fix:** Added an assertion in the never-loads test that no column ends below the card's inner edge, and set the height to 1040px so it holds (all three engines measure -1px).
- **Files modified:** `e2e/widget-layout.spec.ts`, `src/components/LanguagesWidget.svelte`
- **Committed in:** cde4f29
