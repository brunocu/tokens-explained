## Warnings

### WR-01: Focus is lost after a successful "Try again" in the playground (carried over)

**File:** `src/components/Playground.svelte:148-171`
**Issue:** Pressing Try again calls `onLoading`, which sets `download = "loading"` and removes the `{#if download === "failed"}` block that holds the focused button, so focus drops to `<body>`. `onReady` (line 159) only sets state and `readyMessage`, so a keyboard or screen-reader user who retries successfully never lands in the now-editable textarea. Only `onFailed` restores focus. `Comparison.svelte:231-240` handles the same flow with `retriedAttempt` and `focusEnd()`, so the two widgets disagree (WCAG 2.4.3).
**Fix:** Mirror Comparison.
```svelte
let retriedAttempt = false;
function startDownload(retried: boolean): void {
  retriedAttempt = retried;
  void gpt2Download?.start(retried);
}
// in the handlers:
onReady: async (loaded, origin) => {
  tokenizer = loaded;
  download = "ready";
  if (origin === "own" && retriedAttempt) {
    readyMessage = "The tokenizer is ready. You can type now.";
    await tick();
    ta?.focus();
    ta?.setSelectionRange(text.length, text.length);
  }
},
```

### WR-02: The e2e suite still expects the removed Words stat

**File:** `src/components/Playground.svelte:281-294` (the stats block) against `e2e/playground.spec.ts:17`, `:28` and `:92`
**Issue:** The Words stat (`data-stat="words"`) was removed from the playground, but `e2e/playground.spec.ts` still loops over `["tokens", "characters", "bytes", "words"]` and asserts `statValue(page, "words")` has text `2`, a digit string, or `0`. Locators that match nothing time out, so tests (a), (b) and (e) fail. The suite also has no test for the new `[data-show-ids]` switch (the toggle, the helper text change and the chip height change). This was not caught because the last test run recorded in the repository predates the change (HEAD message "test(02.2): complete UAT").
**Fix:** Drop `"words"` from those loops and delete the line-28 assertion. Add a test that clicks `[data-show-ids]` and asserts the helper text and that the chips show their IDs.

### WR-03: Fixed pixel heights are tuned to one machine's fonts; Languages is taller than a laptop viewport (carried over)

**File:** `src/components/LanguagesWidget.svelte:233-236`, `src/components/Playground.svelte:330-333`, `src/styles/widget.css:123`
**Issue:** From 1024px up each widget has `height: var(--widget-h)` (656, 720, 1040px) with `.widget-col { min-height: 0 }` and no `overflow`. The values were measured in Chromium at 1440x900 with the `system-ui` stack, so the slack is about 4px in the playground and zero in the languages widget (the comment says 1040px is the cap and only just holds the failed state). A wider system font, a larger default font size or WCAG 1.4.12 text-spacing overrides wrap one more line in a non-elastic column (the Languages lower-left column holds the picker and the 18px note and has no scrolling) and the content spills over the card padding onto the prose below. The Languages widget is also 1040px high in a 900px viewport, so on a typical laptop the reader cannot see the picker and the results at once.
**Fix:** Use the height as a floor, `min-height: var(--widget-h); height: auto;`. If a fixed height is a hard requirement, add `overflow: auto` to `.widget-col` as a safety net, so overflow scrolls inside the card. Add a test that forces a wider fallback font (`--font-sans: Verdana`) and checks that no column overflows.

### WR-04: Conditionally inserted `role="status"` messages may not be announced; `aria-busy` on the Comparison root (carried over)

**File:** `src/components/Playground.svelte:232-236` and `:253-258`, `src/components/Comparison.svelte:269`, `:307-310`, `:315-317`, `:345`
**Issue:** These `<p role="status">` elements are created together with their text (the loading line, the 1,000-character limit message, the "Getting GPT-2/BERT ready" lines). A live region inserted already holding text is not reliably announced, so the limit message may never be spoken. The code already follows the correct pattern for the load error (`Playground.svelte:240`, always-present wrapper), but not for the others. `Comparison.svelte:269` sets `aria-busy="true"` on the whole root while a tokenizer loads. The `data-announce` region and the BERT status are descendants, and assistive technology may defer changes in a busy subtree. `Playground.svelte:217` puts `aria-busy` on the textarea, which is not a live region.
**Fix:** Keep one empty `role="status"` element mounted for each message and change only its text. Remove `aria-busy` from the Comparison root (or move it to the rows region), and drop it from the textarea.

### WR-05: With the token table open, the playground's chip region can shrink to about one row

**File:** `src/components/Playground.svelte:305-313`, `src/components/TokenTable.svelte:76-83`
**Issue:** The `ScrollRegion` is no longer `fill`, and the table `<details>` now sits below it, outside the region. `TokenTable`'s `.scroll` is now `max-height: 200px`, so an open table takes about 44px (summary) + 200px + gaps. The right column's height is fixed (606px inner), and the heading row, the switch row and the legend (up to three sentences) are fixed too. By my estimate about 100-120px is left for the chip region, less when the legend shows the `[UNK]` and marker sentences. That is one row of ID-stacked chips (about 60px each plus 32px of padding). The region has an automatic minimum size of 0, so it shrinks instead of overflowing. I did not measure this in a browser, and nothing in the e2e suite checks the chip region's height with the table open.
**Fix:** Give the chip region a floor, for example `min-height: 120px` on it via the `class` prop, and let the table's `max-height` shrink (`max-height: min(200px, 30vh)`) or use a smaller cap at 1024px. Add a layout test with the details open and a long default text.
