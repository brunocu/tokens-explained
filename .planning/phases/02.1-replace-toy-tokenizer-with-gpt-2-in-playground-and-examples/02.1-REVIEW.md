# Phase 2.1: Code Review Report

**Reviewed:** 2026-10-07
**Depth:** standard
**Files Reviewed:** 38 (read in full or by phase diff). The other test files and e2e specs in scope were only skimmed. `comparison.json` and the post prose were skipped, as instructed.

## Summary

The phase swaps the toy tokenizer for GPT-2, with a shared memoising loader, a build-time fixture for first paint, and a Try again path. I found no security vulnerabilities and no data-loss bugs.
- Reader text only reaches the DOM through interpolation.
- No `{@html}`, `innerHTML` or `set:html` is used.
- The only network call is the same-origin `fetch` in `loadTokenizer.ts`, and its URL is base-aware.
- The loader evicts failed attempts correctly, including the guard against evicting a newer attempt.
- The byte decoder for GPT-2 is correct.

The real problems are in loading robustness and accessibility of the async states, which the e2e specs do not exercise:
- a stalled download never resolves into the failure state;
- focus is moved unconditionally when async work finishes, and in one place is not restored at all;
- some failure messages are not announced;
- `aria-busy` on the whole comparison card can swallow its own announcements.

Structural findings (fallow): none were provided for this phase.

## Warnings

### WR-01: A stalled tokenizer download never fails, so the card stays locked with no way out

**File:** `src/components/loadTokenizer.ts:31-39`
**Issue:** `download()` calls `fetch()` with no timeout or `AbortSignal`. On a connection that opens but then stalls (captive portal, flaky mobile network), the promise never settles.
- The Playground textbox stays `readonly` and shows "Loading the tokenizer..." forever. No error or Try again button appears, because both only appear on rejection.
- The layout's 8-second watcher does not help, because the island has already hydrated and set `data-state="ready"`.
- The cached promise is also shared, so the Comparison card hangs the same way.
- The e2e "slow download" test delays the response by 9.5 s but always lets it complete, so it does not cover this.
**Fix:** Bound the request and the body read, and let the existing eviction and retry path handle the rejection:
```ts
const DOWNLOAD_TIMEOUT_MS = 30_000;
async function download(id: RealTokenizerId, baseUrl: string): Promise<RealTokenizer> {
  const signal = AbortSignal.timeout(DOWNLOAD_TIMEOUT_MS); // also covers response.json()
  const response = await fetch(tokenizerUrl(id, baseUrl), { signal });
  ...
  const json = (await response.json()) as object;
```
Add a unit test with a never-resolving stubbed `fetch` and fake timers.

### WR-02: Focus is moved unconditionally when async work finishes

**File:** `src/components/Comparison.svelte:188, 195, 211, 216` and `src/components/Playground.svelte:148`
**Issue:** After a download completes or fails, the code calls `focusEnd()` or `retryButton?.focus()` without checking where focus is now. The pressed button is removed from the DOM as soon as the phase flips to loading, so focus falls to `<body>`. The reader may then move on, for example by tabbing to the picker or clicking an example, while the download is still running. When it finishes, focus jumps to the textarea or the retry button, and `focus()` also scrolls the page there.
**Fix:** Move focus only if it was lost, meaning `document.activeElement` is `null` or `document.body`:
```ts
const focusLost = () => !document.activeElement || document.activeElement === document.body;
if (retried && focusLost()) { await focusEnd(); }
```
Apply the same guard before `gpt2Retry?.focus()`, `bertButton?.focus()` and `retryButton?.focus()`.

### WR-03: Playground drops keyboard focus when Try again is pressed and does not restore it on success

**File:** `src/components/Playground.svelte:134-152, 226-230`
**Issue:** Pressing Try again calls `startDownload(true)`, which sets `download = "loading"`. That removes the button (`{#if download === "failed"}`), so focus is lost to `<body>`. On success (lines 138-141) nothing restores focus. Only the failure branch refocuses. `Comparison.svelte` handles this correctly with `focusEnd()` on a retried success. The Playground is inconsistent with it, and a keyboard or screen-reader user has to find their place again.
**Fix:** In the success handler, when `retried` is true (and focus was lost, see WR-02), `await tick(); ta?.focus();`.

### WR-04: Comparison download failures are not in a live region, so they are not announced

**File:** `src/components/Comparison.svelte:293-297, 338-342`
**Issue:** The GPT-2 and BERT error paragraphs (`data-compare-error`) are plain `<p>` elements inserted by `{#if}`, with no `role` and no enclosing live region. They are announced to nobody.
- If GPT-2 fails at page load (`retried` false), a screen-reader user hears nothing, and the textarea simply never appears.
- On a retried failure, only the focused button's name is read, not the reason.

The Playground avoids this by keeping a permanent `<div role="status">` and rendering the error inside it (lines 219-225). The Comparison does not follow that pattern.
**Fix:** Keep an always-present wrapper and render the error inside it, as in the Playground. Alternatively, write the failure text to the existing `announcement` region (`data-announce`) when the phase becomes `"error"`.

### WR-05: `aria-busy` on the whole comparison card can suppress its own announcements

**File:** `src/components/Comparison.svelte:239`
**Issue:** `aria-busy="true"` is set on the card root while GPT-2 or BERT is loading. The card contains the picker and the `data-announce` live region. Assistive tech may defer or drop announcements from inside a busy subtree. The reader can use the picker while GPT-2 is still loading, because it is only disabled on `phase`. The `choose()` message "Showing X. GPT-2: n tokens..." is then written while the container is busy and may never be spoken.
**Fix:** Move `aria-busy` to the element that is actually updating (the rows container or the text block), and keep the live region and picker outside the busy subtree.

## Info

### IN-01: `createRealTokenizer` ignores the `special` flag of added tokens

**File:** `src/core/realTokenizer.ts:94-96` (type at line 19)
**Issue:** `added.get(id)` returns `{content, special}`, but any added token is returned as `special: true` without checking `marker.special`. This is harmless for GPT-2 (only `<|endoftext|>`) and BERT (five specials). It becomes a latent bug if a tokenizer file with non-special added tokens is ever shipped.
- Separately, if a reader types the literal text `[UNK]` into the comparison, BERT returns its real special token and the legend says "the tokenizer had no piece for that word or character and gave up", which is wrong for that input.

**Fix:** Test `marker !== undefined && marker.special`.

### IN-02: Dynamically inserted `role="status"` paragraphs are unreliable announcements

**File:** `src/components/Playground.svelte:212-216`, `src/components/Comparison.svelte:290-292, 337`
**Issue:** These paragraphs are mounted with their text already inside, after hydration. Live regions are announced reliably only when the region exists before its content changes. The loading messages are probably not read.
- The Playground also always announces "The tokenizer is ready. You can type now." (line 141) on every page load, because the download starts at mount. The Comparison deliberately stays silent for a non-retried success, so the two islands are inconsistent.

**Fix:** Decide on one policy. Keep a permanent empty status element per island, write messages into it, and announce the ready message only after a retry, as the Comparison does.

### IN-03: Lookup of reader text in a plain object

**File:** `src/components/Playground.svelte:63`
**Issue:** `preTokens[text] ?? []` indexes a plain object with reader-controlled text. A text like `constructor` or `__proto__` would return a function or object that `?? []` does not replace, and `fixtureTokens` would throw. This is unreachable today because the textbox is read-only until the tokenizer is loaded and the examples are the only other way to set the text. It is a fragile invariant.
**Fix:** Use `Object.hasOwn(preTokens, text) ? preTokens[text] : []`, or pass a `Map` or entries array.

### IN-04: Components cast `comparison.json` themselves instead of using `COMPARISON`

**File:** `src/components/Comparison.svelte:26, 46`, `src/components/LanguagesDemo.svelte:12, 22`, `src/components/LanguagesTable.astro:9, 15`
**Issue:** `src/core/compare/comparison.ts` says components should import `COMPARISON` instead of casting the JSON themselves. Three components still import the JSON and write `as unknown as ComparisonFixture`. The double cast hides any shape drift between the generator and the consumers.
**Fix:** Import `COMPARISON` from `../core/compare/comparison.ts` in all three.

### IN-05: "Module level" comments describe per-instance work

**File:** `src/components/Comparison.svelte:53-65`, `src/components/LanguagesDemo.svelte:26-35`
**Issue:** The comments say "Converted once at module level", but `BY_ID` and `ROWS_BY_ID` are declared in the instance `<script>`. They are rebuilt for every instance and on every server render.
**Fix:** Move them to `<script module>`, or fix the comments.

### IN-06: `engines` allows Node versions that cannot run the project's own scripts

**File:** `package.json:6`
**Issue:** `engines.node` is `>=22.12`, but `precompute:comparison` and `check-core.mjs` import `.ts` files with native type stripping. As far as I recall, that is only unflagged from Node 22.18 (please verify against the Node release notes). Under 22.12 to 22.17 those scripts fail with an unhelpful error. `check-env.mjs` enforces Node 24 only for the e2e path.
**Fix:** Raise `engines.node` to the lowest version with unflagged type stripping, or run the scripts with `--experimental-strip-types`.

### IN-07: The privacy lint misses several exfiltration constructs

**File:** `scripts/check-repo.mjs:14-30`
**Issue:** The ban list covers `fetch(`, XHR, WebSocket, `sendBeacon` and storage. It does not cover `new Image().src = ...`, `EventSource`, `new Worker(url)`, `<link rel=prefetch>` or a dynamic `import("https://...")`. Any of these can leak text without tripping the guard. `check-dist` also scans only URL attributes in HTML and CSS, not JS strings.
**Fix:** Add `\bEventSource\b`, `new\s+Image\s*\(` and `new\s+Worker\s*\(` to `BANNED`, with matching self-test fixtures, and consider a bundle scan for `https?://` in `_astro/*.js`.

### IN-08: Fixed sleeps in e2e specs risk flakiness

**File:** `e2e/playground-load.spec.ts` ("slow download" test, `route` delay of 9500 ms plus `waitForTimeout(9000)`; several `waitForTimeout(300-700)`)
**Issue:** The 9.5 s `setTimeout` inside a route handler plus a 9 s wait exceeds the 8-second watcher by a thin margin and adds about 10 s per browser run. The 500 to 700 ms settles are "a late request would still be caught" heuristics, not guarantees.
**Fix:** Use Playwright's clock control (`page.clock`) to advance past 8 s, and assert on request counts through `expect.poll` or explicit route counters.
