### G1. D-05 leaves a dead end: example chips usable while GPT-2 loads  [VERIFIED: code read + probe]

D-05 keeps the example chips enabled during loading "on the server-rendered default text". But clicking an example changes the text to a string whose tokens the page does not have yet, and `Playground.svelte` derives tokens from the tokenizer only (`const tokens = tokenize(text)` inside `$derived.by`, read this session).

Free fix, no new data: `src/core/compare/comparison.json` already stores GPT-2 rows for all five example texts (`examples[].rows.gpt2`), and the fixture helper `fixtureTokens` turns `{ id, hex }` back into `Token`s. Recommendation: `PlaygroundSection.astro` (server side) builds a small lookup `{ [text]: FixtureToken[] }` for `DEFAULT_TEXT` plus the five `EXAMPLES` (84 tokens in total: 14 default + 16, 19, 9, 16, 10 from the fixture pins) and passes it as a prop; while `data-tokenizer != ready` the island reads tokens from that lookup (the textbox is locked, so `text` is always one of those six strings, and Reset sets `DEFAULT_TEXT`). Counts of characters and words never needed the tokenizer. Do not import `comparison.json` inside the island (it would put 60 to 80 KB of JSON in the client bundle); select the six entries in the `.astro` wrapper. Pass `FixtureToken` (`id` + uppercase hex), not `Token`, as the existing Comparison island does; convert in the island.
Fallback if the planner prefers simplicity: disable the example chips until ready (contradicts a literal reading of D-05, so confirm with the user first; see Open Question 1).
For D-07 the default text still goes into the fixture generation: add it to `buildComparison` input (`scripts/lib/comparison-build.ts` builds from `examples` and `languages` only today) with a freshness assertion `fixture.<key>.text === DEFAULT_TEXT`.

### G2. Build-time GPT-2 in Astro frontmatter works; recipe verified  [VERIFIED: prototype build this session]

Open question was whether `.astro` frontmatter can load the GPT-2 file and the library for the prose figures, the bridge figure and `assertClaims`. A scratch copy of the repo (outside the repo, `node_modules` symlinked) with `ToyTokens.astro` switched to the helper below built cleanly (`astro build`, 2 pages), the figure rendered GPT-2 chips (`Token`, 210 `data-chip` in the post page), and the client output is unchanged (`tokenizers.*.js` chunk is the existing `loadTokenizer` dynamic import).

```ts
// src/core/buildTokenizer.ts  (Node only; imported by .astro frontmatter, claims tests, scripts)
import { readFileSync } from "node:fs";
import { createRealTokenizer } from "./realTokenizer.ts";
import type { RealTokenizer, TokenizerCtor } from "./realTokenizer.ts";
let memo: Promise<RealTokenizer> | undefined;
export function buildGpt2(): Promise<RealTokenizer> {
  memo ??= (async () => {
    const json = JSON.parse(readFileSync(`${process.cwd()}/public/tokenizers/gpt2.json`, "utf8")) as object;
    const { Tokenizer } = await import("@huggingface/tokenizers");
    return createRealTokenizer("gpt2", json, Tokenizer as unknown as TokenizerCtor);
  })();
  return memo;
}
```

Notes: use `process.cwd()` (project root during `astro build`, `astro dev`, Vitest, and the existing tests already use root-relative `public/tokenizers/gpt2.json`); `import.meta.url` is unreliable inside Astro's bundled server chunks. Frontmatter uses top-level `await`. Memoise so the 50 ms build happens once per build. `realTokenizer.ts` and the library also load in plain native Node (probe: `createRealTokenizer` + `dist/tokenizers.mjs` under Node v24.21.0), so `scripts/check-core.mjs` can replace its toy half with a GPT-2 smoke check the same way `scripts/precompute-comparison.ts` already does.

Claims (D-11) shape: make `checkClaim(text, claim, tokenizer)` take the tokenizer (Vitest tests load it in `beforeAll` like `realTokenizer.test.ts`; `ToyTokens` replacement passes `await buildGpt2()`), keep `assertClaims` called from the figure so a false claim still fails the build. `presplit.ts` goes away, so claims needs a local word matcher; `/ ?\p{L}+/gu` reproduces the old shape (letters with optional leading space, same boundary GPT-2's own pre-tokenizer cuts at). All four claims hold for the unchanged `DEFAULT_TEXT` under GPT-2: 14 tokens vs 11 words, `Token` + `ization` split, ` splits` has a leading space, ` common` is one token [VERIFIED: probe output, tokens `30642:"Token" 1634:"ization" 30778:" splits" ... 2219:" common"`]. The test cases in `claims.test.ts` built around "hello is three tokens" must be rewritten (under GPT-2 `hello` is one token, per EVALUATION 3.1).

### G3. The post's number rule cannot carry GPT-2-derived numbers as written (affects D-12, D-13)  [VERIFIED: post-content.test.ts read]

- `<Fact of="...">` resolves through `fact()` in `src/core/stepper.ts`, which is synchronous and reads only `STEPPER_FACTS`; the content test asserts `Object.hasOwn(STEPPER_FACTS, key)` for every `<Fact>`. There is no way today to print "83" (GPT-2's id for `t`).
- The number test only allows numbers that are `0`, `1`, a `<Fact>`, or listed in `CITED` with a cite to a matching source. A hand-typed 83 fails the content test (this is the rule D-13 cites).
- Recommendation: add a second fact source, e.g. `src/core/gpt2Facts.ts` exporting the key list `GPT2_FACT_KEYS` (`idOfT`, `idOfSpace` if wanted) and `async gpt2Facts()` computed from `buildGpt2()`; `Fact.astro` looks the key up in STEPPER_FACTS first, then in `await gpt2Facts()`; extend the content test's `<Fact>` key check to accept either source; add a unit test pinning the engine values. Verified values this session [VERIFIED: probe over `public/tokenizers/gpt2.json`]: `"t"` encodes to id `83`, `"at"` to `265`, `" "` to `220`; stepper side `STEPPER_FACTS` = `{"byteOfT":116,"byteOfSpace":32,"endPieces":20,"wordCount":13,"firstNewId":256, ...}` (printed by the probe).
- D-12 prose: GPT-2 cuts the cat-sat sentence into 13 tokens, one per word [VERIFIED: probe: 13 tokens for `the cat sat on the mat and the cat sat on the hat`, ids `1169 3797 3332 319 262 2603 290 262 3797 3332 319 262 6877`]. Write "one token for each word" and let the figure caption (generated) state the count; use `<Fact of="endPieces" />` for the stepper's 20. Do not type "13" or "20" (body test rejects `\d+ tokens`, and bare numbers need a source).
- Word budget: `wc -w` on `what-is-a-token.mdx` is 2,566 today and the ceiling test is 2,750, so about 184 words of headroom (the test comment's "2671" is stale). Bridge paragraph, id sentence and the D-14 note must fit in roughly 150 net words or the ceiling must be raised in the same change (rounded as the test comment describes).

### G4. `loadTokenizer` memo (D-08) breaks existing unit tests unless designed for it  [VERIFIED: loadTokenizer.test.ts read]

Existing tests call `loadTokenizer("gpt2", "/")` repeatedly across `it` blocks, then expect a 404 rejection for `("gpt2", "/")` again. A module-level memo keyed by id alone would (a) return the cached success in the 404 test and (b) skip the second request in the base-path test. Required design: key by `${baseUrl}|${id}`, evict the entry when the promise rejects (so Try again refetches), and export a `resetTokenizerCache()` test hook called in `afterEach` (or use `vi.resetModules()`). New tests: two concurrent calls make one request; a rejected load is retried by the next call; success is shared. Also update the header comment (it says "Only the caller's click handler may call this function", now false: Playground calls it in `onMount`) and the matching sentence in the `scripts/check-repo.mjs` header ("on a button press"). The lint itself only checks the path, not the comment.

Cross-island sharing is free: the Playground and Comparison islands import the same module, so one memo map serves both within a page. `OwnText` should call `loadTokenizer("gpt2", baseUrl)` on mount (memoised, usually already resolved or in flight) and keep the click only for BERT (D-09). Its `Rows` type, `result` derivation (currently returns empty rows unless both tokenizers are loaded), announcement text and table list must handle "GPT-2 ready, BERT not yet". Per-file size labels: the manifest already has `gzipBytes` per file (`gpt2` 548865, `bert` 190756); `sizeLabelMb` gives `"0.5"` and `"0.2"`. `ComparisonFixture.meta.download` currently holds only the combined figure (`combinedGzipBytes: 739621`, pinned "0.7" in `fixture.test.ts`), so change it to per-tokenizer sizes; the playground status line should take its "about 0.5 MB" from the same source, not hand-typed.

### G5. Hydration directive and what waits on "ready" (D-04, D-07)  [CITED: docs.astro.build/en/reference/directives-reference/]

`PlaygroundSection.astro` uses `client:visible` today. Astro docs: `client:load` "Load and hydrate the component JavaScript immediately on page load"; `client:idle` hydrates "once the page is done with its initial load and the `requestIdleCallback` event has fired"; `client:visible` once the component enters the viewport. For D-04 use `client:load` (starts the fetch at page load; `client:idle` is an acceptable softer choice for Phase 5 budget). Keep the fetch in `onMount` through `loadTokenizer`; the file stays out of the bundle because `loadTokenizer` uses `fetch` plus a dynamic import of the library.

`BaseLayout.astro` watcher flips only `[data-island]` cards whose `data-state` is `"loading"` after 8 s; it never reads other attributes. So: set `data-state="ready"` in `onMount` as today and put download progress on a different attribute (D-07 suggests `data-tokenizer="loading|ready|failed"`). No watcher change needed. Do not reuse `data-state` for the download.

Every e2e spec that types into the playground currently waits for `data-state="ready"` and then types (e.g. `playground`, `controls`, `states`, `frames`, `resilience`, `privacy`, `a11y`, `post` lines 49 and 64, `phone-width`, `smoke`). With D-07, `ready` arrives before the textbox unlocks, so each must also wait for `data-tokenizer="ready"` (textbox editable). `e2e/` has no shared helper file today (`states.spec.ts` has a local `openReady`); add one `e2e/helpers.ts` (`openPlaygroundReady(page)`) rather than editing 10 copies. `privacy.spec.ts` test 1 asserts zero requests after "ready"; it must wait for the tokenizer to be ready and the network to go idle first, then keep the zero-request assertion for typing. Test 2 must be rewritten: the post page now requests `gpt2.json` once (assert exactly one request, proving D-08), and `bert-uncased.json` zero times until the button is pressed.

### G6. `states.spec.ts` test (g) hook still works with GPT-2 (corrects EVALUATION 5.7)  [VERIFIED: probe]

EVALUATION 5.7 says the `TextEncoder.prototype.encode` break hook "needs replacing" because the library does not use `TextEncoder` the same way. Probed: in `node_modules/@huggingface/tokenizers/dist/tokenizers.mjs` the byte-level pre-tokenizer does `this.text_encoder = new TextEncoder()` (line 1135) and, after patching `TextEncoder.prototype.encode` to throw, the GPT-2 adapter's `tokenize("something new")` and `tokenize("hello")` throw `encoder broken` while `tokenize("")` returns 0 tokens (the empty string never reaches the encoder). So the existing injection still produces the error state in the new Playground, provided the break flag is set after `data-tokenizer="ready"`. Keep test (g) with only the wait changed. Keep the `try/catch` around the tokenize call in the new `$derived` so the existing `[data-tokenizer-error]` copy keeps working; the new load-failure message must be a different element (for example `data-tokenizer-load-error`) so the two failure tests do not collide.

### G7. Playground legend needs wording for GPT-2's special chip  [VERIFIED: TokenLegend.svelte read]

`TokenLegend.svelte` takes `special?: boolean` and, when true, prints the fixed sentence "`[UNK]` means the tokenizer had no piece for that word or character and gave up." That is false for GPT-2's only special token, `<|endoftext|>` (id 50256 in the hosted file [VERIFIED: `tj.added_tokens` = `[[50256,"<|endoftext|>"]]`]). EVALUATION 5.3 says "add a legend line"; the concrete constraint is that the prop must become a kind (for example `special?: "unknown" | "marker"` or two booleans) so the playground never shows the `[UNK]` sentence. `OwnText`/`Comparison` can show both when both appear. Update the `[data-legend]` assertions in `a11y-phase2`/`comparison` specs accordingly.

### G8. D-14 source check: what may and may not be claimed about GPT-2 vs newer tokenizers  [VERIFIED: primary sources fetched this session]

- **Hosted file is OpenAI's original vocabulary.** Downloaded `https://openaipublic.blob.core.windows.net/gpt-2/encodings/main/encoder.json` (1,042,301 bytes) and `vocab.bpe` (456,318 bytes) and compared with `public/tokenizers/gpt2.json`: `encoder.json` has 50,257 entries, 0 differ from `model.vocab`; `vocab.bpe` has 50,000 merge lines, identical in order to `model.merges`; the hosted file adds one special token, `<|endoftext|>`, id 50256. So "50,257 entries" is exact and "GPT-2's tokenizer" is not a third-party approximation. (`openai/gpt-2` `download_model.py` lists `encoder.json` and `vocab.bpe` among the files it downloads from `https://openaipublic.blob.core.windows.net/gpt-2/`.) The post already cites 50,257 with refs 16 and 18; do not add the number 50,000 (the content test's `CITED` map would need a new entry and a source).
- **Licence wording.** `openai/gpt-2` LICENSE begins "Modified MIT License / Software Copyright (c) 2019 OpenAI / We don't claim ownership of the content you create with GPT-2, so it is yours to do with as you please."; the Hugging Face API for `openai-community/gpt2` reports `cardData.license: "mit"`. `public/tokenizers/NOTICE.md` already records this (it says the HF repo ships no LICENSE file, and quotes OpenAI's). Safe wording: "released under a permissive MIT-style licence", not a bare "MIT".
- **Do not contrast "open" against newer GPT tokenizers.** The cited sources (refs 18, 19, tiktoken, MIT licence per `raw.githubusercontent.com/openai/tiktoken/main/LICENSE`: "MIT License / Copyright (c) 2022 OpenAI, Shantanu Jain") publish `cl100k_base` and `o200k_base` as downloadable vocab files in `tiktoken_ext/openai_public.py`, which carries no licence comment for those data files. So newer tokenizers are also public; their data-file licence is simply not stated in that source. Claims that are supportable: GPT-2 is small (50,257 vs 200,019 entries, already cited; file size is a build-time/manifest fact), it is old (2019, already in `rows.ts`), its design is published (paper, ref 16, plus the released files above), and both shipped files are under licences that allow self-hosting (manifest). Claims to avoid: "newer tokenizers are closed/not free", any file-size comparison with `cl100k`/`o200k` (the only figures in the project are from an unverified HF mirror, CLAUDE.md marks its licence LOW).
- **No new link host needed.** `scripts/check-dist.mjs` `ALLOWED_REFERENCE_LINK_HOSTS` already includes `github.com`, `cdn.openai.com`, `arxiv.org`; a new reference to `github.com/openai/gpt-2` is allowed. Any new reference needs an access date, and the "every reference is cited, numbered in first-cite order" tests apply.

## Don't Hand-Roll

| Problem | Use instead |
|---|---|
| Per-load request sharing | one module-level promise map in `loadTokenizer.ts`, keyed `baseUrl|id`, evicted on reject |
| Token props across the island boundary | the existing `FixtureToken` (`id` + hex) and `fixtureTokens()`, not raw `Uint8Array` props |
| Build-time GPT-2 | `buildGpt2()` memo above, reusing `createRealTokenizer` (do not write a second adapter) |
| Size labels | `sizeLabelMb(manifest gzipBytes)`, never hand-typed |

## Common Pitfalls

1. **Memo breaks old loader tests / caches failures.** Key by base + id, evict on reject, add a reset hook (G4).
2. **Reusing `data-state` for the download** trips the 8 s watcher on slow links. Use `data-tokenizer` (G5).
3. **Example chips enabled with no tokens available** (G1).
4. **`[UNK]` legend sentence shown for `<|endoftext|>`** (G7).
5. **Hand-typed GPT-2 numbers in prose** fail the content number rule; add a GPT-2 fact source (G3).
6. **Importing `comparison.json` in the Playground island** bloats the bundle; slice it in the `.astro` wrapper (G1).
7. **Word ceiling (2,750)** has only about 184 words of headroom (G3).
8. **Over-claiming about newer tokenizers** in the D-14 note (G8).
9. **Two failure tests colliding** (`data-tokenizer-error` for runtime failure vs a new load-error element) (G6).
