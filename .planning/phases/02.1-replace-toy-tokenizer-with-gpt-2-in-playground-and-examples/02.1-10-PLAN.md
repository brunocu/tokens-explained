## Goal

Back online, one press of Try again on the GPT-2 download unlocks every widget that was waiting on that file, not just the one that was pressed.

Source: UAT test 3, gap G-02.1-3 (severity major). Root cause (from 02.1-UAT.md): each widget keeps its own failed state and calls the loader on its own; the loader evicts a failed attempt, so a retry in one widget starts a request only for that widget, and nothing tells the other widgets' settled, failed promises that a later attempt succeeded.

This is gap closure for a finished phase: the architecture is already proven end to end, so there is no separate tracer task. The plan changes plan 02.1-06's accepted behaviour "each island's Try again is independent" (Comparison.svelte header comment, e2e `(c2)`): independence of the Try again button stays, independence of the outcome goes.

## Flagged assumptions and planner choices

- Chosen option from the UAT "missing" list: a shared signal from the loader that failed widgets listen to. Rejected alternative, "Try again retries every failed widget": it would start a second request per widget on the sibling's behalf and would still need a way to move focus and announcements only in the pressed widget.
- The signal fires from inside the loader's own attempt (the first `then` on the download promise), once per successful download of a base-plus-id key, with the built tokenizer. It does not replay to late subscribers: a late widget calls `loadTokenizer`, which returns the memoised success at once. Listener exceptions are caught so a faulty listener can neither reject the load nor starve other listeners.
- A widget acts on the signal only while it is in its failed state. A widget that is idle, loading (its own attempt, which gets the same tokenizer through its own promise) or already ready ignores it. This is what keeps focus and announcements with the pressed widget: the pressed widget is in "loading" when the signal arrives, so it takes its normal own-attempt path.
- Both widgets repeat the same state machine (start, retried flag, mounted guard), so it moves into one small plain-TypeScript controller, `src/components/tokenizerDownload.ts`. That also makes the behaviour testable under the Vitest `node` environment (there is no DOM test setup and `onMount` does not run in server rendering). The controller makes no network call itself, only calls `loadTokenizer`; `scripts/check-repo.mjs` needs no change.
- Silent adoption in a cleared widget sets its state and tokenizer only. No `readyMessage`, no `announcement`, no `focus()`. The error paragraph in the playground sits in an always-present `role="status"` wrapper; removing its text is not announced as new speech, which is the accepted quiet behaviour for the non-pressed widget. If focus was on a Try again button that disappears, the browser moves it to the document; this is accepted because the reader pressed Try again elsewhere.
- Not in scope: BERT (its download starts only from the card's own button, so no other widget can be waiting on it), stalled-download timeouts (WR-01, deferred to Phase 5 by the UAT test 3 text), and any change to FOUND-07/TOK-07 status (they stay Complete; this plan only repairs a retry behaviour of the verified feature, requirement ids are listed for traceability).

<objective>
Add a success signal to the shared tokenizer loader, put the retry-and-recover logic into a small shared controller, use it in the playground and the comparison card, and prove with Vitest and one updated end-to-end spec that a retry in one widget clears the error in the other without moving focus or announcing there.

Purpose: close G-02.1-3 (UAT test 3 truth: "Back online, Try again unlocks the textbox (and clears the error) in every widget using the GPT-2 tokenizer").
Output: loader signal, controller, two edited widgets, unit tests, updated and new end-to-end specs.
